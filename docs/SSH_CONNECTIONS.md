# SFTP: SSH config и промежуточные серверы

Добавлено в исходники после опубликованного 0.7.0. Используйте свежую локальную сборку.

В **Сеть → Подключиться** выберите SFTP. Кнопка **Импорт SSH config…** предлагает файл и имя из `Host`, затем заполняет редактируемый профиль. Импорт создаёт новый профиль без сохранённого пароля. Это снимок параметров: дальнейшие изменения исходного файла требуют повторного импорта.

Кнопка **Промежуточные SSH-серверы…** открывает до четырёх переходов в порядке подключения. Для каждого задаются адрес, порт, пользователь и необязательный путь к ключу; пустой путь означает agent/стандартные ключи. У каждого узла, включая конечный сервер, выбирается способ входа: ключ/agent, пароль или «Интерактивный / MFA». Пароль промежуточного узла запрашивается при подключении к нему и не записывается в профиль. Изменение цепочки очищает введённый пароль конечного сервера.

Ключ каждого узла проверяется отдельно. Для нового ключа приложение показывает конкретный адрес и отпечаток; подтвердите его после сверки с владельцем сервера. Изменённый ключ останавливает подключение. Наличие доверенного промежуточного узла не означает доверие конечному.

## Интерактивный вход / MFA

В основном окне выберите **Способ входа SFTP → Интерактивный / MFA**. Для промежуточного узла выберите этот же режим в его строке; обычный парольный вход на узел задаётся вариантом **Пароль**. При необходимости укажите закрытый ключ для сочетания «ключ + код».

Каждый запрос открывается отдельно: сверху указан проверенный сервер, пользователь и номер перехода, ниже — буквальный текст запроса SSH. Введите пароль, одноразовый код или иной ответ. Все ответы маскируются; пустой ответ допустим, если его требует сервер. **Отмена** прерывает вход, таймаут закрывает запрос и не позволяет отправить устаревший ответ. Время ввода входит в общий таймаут подключения; для MFA его можно увеличить в основном окне.

Поддержан SSH keyboard-interactive: несколько вопросов в одном раунде, несколько раундов и предварительный вход по ключу с последующим кодом. Требование дополнительных факторов задаёт сервер. Перед любым запросом проверяется ключ соответствующего узла. Пароль конечного сервера не подставляется в запросы переходов.

Ответы интерактивного режима и пароли переходов не сохраняются в JSON, Keychain, аргументах процесса, окружении или обычных временных файлах. Автоматическое сохранение введённой фразы закрытого ключа средствами OpenSSH также отключено в интерактивном режиме. Ранее добавленные в agent ключи можно использовать. Обычный пароль конечного сервера по-прежнему можно сохранять по отдельной отметке в основном окне.

Ограничения: до 16 запросов на SSH-процесс, текст запроса до 4096 байт UTF-8, ответ до 1023 байт без NUL и переводов строки. OpenSSH не передаёт askpass признак открытого ввода, поэтому все поля скрытые. Заголовки и инструкции, которые сервер отправляет отдельно от вопроса в stderr, не показываются; браузерные схемы MFA не заявлены. Новая SSH-сессия снова запрашивает вход. В пределах открытого подключения файловые операции переиспользуют уже аутентифицированную SFTP-сессию и всю цепочку переходов; ответы и OTP не кэшируются.

## Импортируемые параметры

- `Host` с `*`, `?` и отрицаниями; первое применимое значение параметра имеет приоритет.
- `HostName`, `User`, `Port`, `ConnectTimeout`, один `IdentityFile` на сервер.
- `ProxyJump`: один узел или список через запятую; псевдонимы, `user@host:port`, SSH URI и IPv6 в скобках. Настройки первого перехода могут задавать предшествующие переходы; явно перечисленная цепочка имеет приоритет над `ProxyJump` последующих узлов.
- `Include` с масками в лексическом порядке. Относительные пути считаются от каталога выбранного главного файла: для `~/.ssh/config` это `~/.ssh`. Вложенные файлы используют тот же базовый каталог.
- `~`, `~/`, `%%`; для `Include` — `%d/%u`, `HostName` — `%h`, `IdentityFile` — `%d/%h/%n/%p/%r/%u`, `ProxyJump` — `%h/%n/%p/%r`.
- `IdentitiesOnly yes` при заданном ключе, `IdentitiesOnly no` без явного ключа; совпадающие с режимом приложения `UseKeychain yes`, `AddKeysToAgent no`, `ForwardAgent no`. Противоречащие режиму значения отклоняются.

Пример:

```sshconfig
Host work
    HostName files.internal
    User ivan
    ProxyJump gateway
Host gateway
    HostName gateway.example.org
    User ivan
    IdentityFile ~/.ssh/id_ed25519
```

`Match`, `ProxyCommand`, `LocalCommand`, пользовательский `IdentityAgent`, сертификаты пользователя, несколько различных ключей, переменные окружения и другие не представимые в профиле настройки дают явную ошибку. Команды из config не запускаются. Настройки оформления, журналирования, keepalive и окружения сеанса не импортируются: ими управляет приложение. Полная совместимость со всем языком OpenSSH config не заявлена; остатки сохранены в R16.

Импорт SSH config по-прежнему переносит основной набор параметров и создаёт узлы в режиме ключа/agent. Парольный или интерактивный режим выберите в форме после импорта; расширенные директивы аутентификации остаются за пределами импортируемого поднабора.

Пределы импорта: 1 МиБ текста, 64 файла, восемь уровней Include и четыре перехода. Циклические включения и повторяющиеся адреса с одинаковым портом отклоняются. Системный SSH config автоматически не подключается.

## Транспорт и проверки

Каждый переход создаёт отдельное соединение системным OpenSSH без удалённого shell и без передачи agent на сервер. Служебные порты слушают только loopback; приватный управляющий сокет подтверждает готовность именно созданного процесса. Подлинность проверяется по исходному адресу узла, а не по временному локальному порту. Пароль конечного сервера передаётся только его SSH-процессу после установления переходов; интерактивные запросы каждого процесса привязаны к своему исходному адресу. Ответы проходят через отдельные приватные FIFO. Автоматическая очистка после ошибки или отмены не открывает новые запросы входа; если без них очистка невозможна, временный серверный файл может остаться. Отмена активного запроса, транспортная/протокольная ошибка и явное отключение закрывают цепочку в обратном порядке; успешное завершение оставляет её для следующей операции.

Тесты используют два изолированных SSH-сервера переходов и SFTP-сервер, недоступные по своим именам напрямую с клиента. Проверяются импорт маршрута, байты файлов, отдельное доверие каждому узлу, подмена ключей, отмена на переходе и при входе на конечный сервер, таймаут, закрытие соединений и отсутствие парольных попыток на переходах. Тестовый Paramiko в приложение не включается.

## Переиспользование подключения

Одна открытая SFTP-панель сохраняет свою аутентифицированную сессию и до четырёх переходов между листингом, проверкой свойств, скачиванием, отправкой, переименованием и удалением. Поэтому обход дерева, проверка записанных байтов и работа редактора используют уже пройденный MFA. Одновременные запросы одного подключения выполняются последовательно; ожидание можно отменить, а его таймаут не прерывает текущую команду. Таймаут I/O начинается заново для каждого запроса, время простоя в него не входит. Токен завершённой операции больше не управляет соединением.

Сессия принадлежит одному экземпляру подключения: другие панели/профили не получают её через общий сокет. Изменённые параметры создают новый экземпляр. Изменение содержимого known_hosts приложения или явно выбранного ключа сбрасывает сессию перед следующей командой; проверка ключей узлов снова предшествует любому паролю/коду. Файл known_hosts и явно выбранные ключи должны быть обычными файлами до 1 МиБ; FIFO, устройства и каталоги отклоняются. Для явно выбранного ключа допустима ссылка на обычный файл; её цель входит в снимок. Изменения исходного SSH config требуют повторного импорта. Приватный управляющий сокет перехода остаётся только внутри принадлежащей этому подключению цепочки; внешние ControlMaster-сокеты не используются.

Выход из сетевой панели, команда переподключения и штатное завершение приложения закрывают соединение. Отмена активного запроса, таймаут ответа, обрыв связи или повреждённый пакет уничтожают текущую сессию и переходы. Фоновая очистка не открывает новую сессию. Следующая явная команда пользователя может подключиться заново и запросить MFA; автоматического повтора неоднозначной записи нет. Полный ответ SFTP STATUS, например «нет файла» или «нет доступа», сохраняет здоровую сессию при закрытых файловых дескрипторах. После отмены отправки приватный серверный `.farmac-upload-…` может остаться.

Проверки на реальном системном OpenSSH и локальных SSH/SFTP-серверах считают успешные входы: последовательные файловые операции и оба перехода выполняются после одного MFA на узел. Дополнительно проверяются изоляция экземпляров, отменённый старый токен, ожидание конкурентной команды, таймаут, переподключение, изменение доверия, отключение из callback и потеря ответа после выполненного rename. Это переиспользование живого соединения в текущем процессе; сохранение сеанса после перезапуска не заявлено.
